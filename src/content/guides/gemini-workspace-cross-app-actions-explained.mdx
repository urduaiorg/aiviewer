*AIViewer editorial system · September 25, 2026*

Google's September Workspace update brings cross-app creation into familiar work surfaces: a request in one app can produce a working file in another. The practical opportunity is to reduce the manual transfer of information. The practical challenge is to preserve its meaning while changing its format.

Consider an email thread with a revised deadline, a proposed purchase and an unanswered question. A useful project brief must retain those distinctions. A polished document that converts all three into settled decisions can create more work than it saves.

**Five workflows Google describes**

Google's September 9 announcement presents these examples. They describe provider capabilities, not results from an AIViewer test.

| Starting point | Requested output | What the user receives |
| --- | --- | --- |
| Chat | Project update presentation | A linked Slides draft assembled from project context. |
| Drive | Project spreadsheet | A structured Sheet based on the folder and selected sources. |
| Docs | Team email | A contextual draft to review, address and send. |
| Gmail | Project brief | An editable Doc drawn from the thread and relevant context. |
| Docs | Branded presentation | A Slides deck using the proposal and supplied style references. |

The announcement describes Chat access as arriving in the coming weeks and says these capabilities will also come to Workspace Studio flows. It does not establish that every account already has either experience. The clarification-question experience for presentation creation is also described as forthcoming. **Choose context deliberately**

Google's source guide says added files remain active through a conversation and that previous-turn sources can still be referenced. Start a fresh conversation when excluding earlier material, then inspect source settings. Administrator-enabled app data can also contribute context. Google cautions that a source list can be incomplete or inaccurate and that oversized inputs may not all be processed. [Source selection and limitations](https://support.google.com/drive/answer/16813283?hl=en)

Administrators can control active search across Workspace services; changes may take up to 48 hours. Disabling a service as a search source does not necessarily exclude specifically referenced or currently open content. These settings concern Workspace Intelligence, not every separate Gemini service. [Administrator controls](https://knowledge.workspace.google.com/admin/generative-ai/workspace-intelligence/control-workspace-intelligence)

For a project brief, write down the intended evidence set before asking for a draft. Include the latest decision record and identify obsolete material. The objective is not simply to supply more documents. It is to make the relevant decisions traceable.

**Worked example: a thread with a changing deadline**

The following messages are entirely fictional. They were written for this article and are not a transcript of real email or a test of Gemini. Imagine an internal team arranging a training session. All dates refer to 2026; no calendar invitations have been created.

| Source | Fictional message |
| --- | --- |
| A — September 21, Mira | “Proposal: run the staff workshop on October 6. Working budget ceiling: PKR 60,000. Please wait for my final date confirmation.” |
| B — September 22, Hamza | “The venue quote is PKR 35,000. Catering would add PKR 12,000. Both are quotes only; neither is approved or booked.” |
| C — September 23, Mira | “Confirm October 8 instead of October 6. Keep the PKR 60,000 ceiling. I will approve or reject the supplier quotes after reviewing them.” |
| D — September 24, Sana | “I will prepare the attendance form by October 2. We still need someone to own the invitation email; please do not assign it to me by default.” |

A useful drafting request would be:

> Using only the supplied fictional messages A–D, write an internal project brief. Separate confirmed decisions, quotes awaiting approval, assigned tasks and open questions. Cite message letters beside each important claim. Preserve corrected dates. Use “unassigned” where no owner accepted a task. Do not invent bookings, payment status or deadlines. Produce a draft for review; do not send messages or schedule events.

This instruction defines the desired output. It does not itself configure product access or guarantee that other context is excluded. Check the source controls separately.

**Reference brief and answer key**

The following is an authored reference answer, not a model response:

- **Purpose:** arrange a staff workshop. [A]
- **Confirmed event date:** October 8, 2026. The earlier October 6 proposal is superseded. [C]
- **Budget ceiling:** PKR 60,000. [C]
- **Quoted costs:** venue PKR 35,000; catering PKR 12,000; combined PKR 47,000. Neither item is approved or booked. [B]
- **Arithmetic gap below the ceiling:** PKR 13,000, calculated as 60,000 minus 47,000. This is not confirmed spare cash or a complete event-cost estimate. [B, C]
- **Assigned work:** Sana prepares the attendance form by October 2. [D]
- **Decision pending:** Mira reviews the supplier quotes. No decision deadline is specified. [C]
- **Open ownership question:** the invitation email has no assigned owner or deadline. [D]

Each qualifier does work. “Quoted” preserves procurement status. “Superseded” prevents the earlier date from surviving as a competing commitment. “Unassigned” prevents a person mentioned in a thread from silently becoming responsible for a different task.

Now compare this **deliberately flawed, authored summary**:

> The workshop is booked for October 6. Sana will send invitations by October 2. Approved spending is PKR 47,000, leaving PKR 13,000 available for purchases.

Four corrections are needed. The confirmed date is October 8. No booking is established. Sana's October 2 task is the attendance form, not invitations. The costs are unapproved quotes, and the difference below a ceiling is not purchasing authorization.

For a variation, remove message C from the evidence set. The correct brief can no longer claim October 8 is confirmed. It should retain October 6 only as a proposal awaiting confirmation. This exercise shows why a coherent draft can still be wrong when its sources are incomplete.

**Review before the next action**

A document draft, an email and a calendar event have different consequences. Use a short review sequence before moving between them:

| Check | Apply it to the fictional workshop |
| --- | --- |
| Date and version | Confirm that the brief uses C to supersede A. |
| Owner and deadline | Keep Sana's form deadline separate from the unassigned invitation. |
| Number and status | Recalculate PKR 47,000 and PKR 13,000; retain “quotes only.” |
| Audience | An internal brief can contain an unresolved discussion that does not belong in a final attendee invitation. |
| Action | Review recipients and final wording before sending; review event details before confirming a calendar commitment. |

Do not turn the exercise into a real invitation. Its names, costs and dates are practice material. To apply the method at work, replace them with approved sources and record what you checked. Our guide to [verifying an AI answer](/guides/how-to-verify-an-ai-answer/) develops that process further.

The value of cross-app assistance will depend on the whole task: finding the right sources, making a usable draft, correcting it and approving the next step. A sensible first trial is one internal brief with known inputs and an answer key. If you can trace its dates, figures and owners back to evidence, you have a stronger basis for deciding what to delegate next.
